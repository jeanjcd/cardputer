# セキュリティ

このページでは、M5-Mesh-Hello v0.1.0 が何を保護し、何を保護しないか、そしてリリースを検証する方法を説明します。脆弱性を報告するには [SECURITY.md](../../SECURITY.md)（英語）に従ってください。公開の issue は作成しないでください。

## 脅威モデル

| 攻撃者 | 能力 | 主な懸念 |
|---|---|---|
| **LoRa 経由のリモート攻撃者** | 離れた場所から、リージョンの周波数で任意のフレームを送信できる | 不正なフレームによるメモリ破壊やクラッシュ、復号の回避、デバイスに送信を強いること（電波の濫用）、ストレージの枯渇 |
| **悪意のある、またはなりすましの Meshtastic ノード** | 任意の `from` ノード番号、名前、鍵を持つ正しい形式の Meshtastic フレームを送信できる | 他のノードへのなりすまし、相手の鍵の置き換え、NodeInfo 要求の大量送信、あいさつを大量に送らせること |
| **物理的なアクセス** | デバイスやそのフラッシュチップを手にしている | 秘密鍵の読み出し、保存された相手や設定の読み出し、改造したファームウェアのインストール |
| **サプライチェーン** | 依存関係、CI、公開されたバイナリを改ざんする | ビルドや `bin/` への悪意のあるコードの混入 |

## 保護

### 信頼できない無線入力

- **無線からのすべてのバイトを信頼しません。** ヘッダーパーサー、protobuf デコーダ、復号処理、アプリケーションロジックは、すべての長さとインデックスを固定サイズのバッファに照らしてチェックします。255 バイトを超えるフレーム、239 バイトを超えるペイロード、末尾を越える protobuf フィールド、大きすぎる `payload` フィールド、32 バイトでない公開鍵は拒否されます。
- **受信経路でヒープを確保しません。** すべてのバッファは固定サイズで、大きなデコード済み構造体は静的です。
- **ファジングとサニタイザ。** `test/test_fuzz` は、ランダムなフレームと変異させたフレーム 200,000 個をプロトコルデコーダ（`headerParse`、protobuf デコーダ、`pkiDecrypt`、`parseFrame`）に流します。その上のアプリケーション層（`src/app/` の `App::handleFrame`）はデバイス上でのみ動作し、ファジングの対象ではありません。その判断ロジック（ノード表、送信箱、レート制限、設定）は `src/mesh/` で単体テストされています。CI は、ファジングテストを含むすべてのネイティブテストを AddressSanitizer と UndefinedBehaviorSanitizer の下で実行します。
- **静的解析。** CodeQL（`security-extended`）がすべての push とプルリクエスト、および毎週実行され、その結果はリポジトリの Security タブに表示されます。解析するのはネイティブテストのビルド、つまり `src/mesh/` の移植性のあるコアとテストです。`src/app/` と `src/hw/` のデバイス専用コードはそこではコンパイルされないため、解析されません。検出結果があればジョブは失敗します。

### 暗号

- DM は、Meshtastic と同様に 8 バイトのタグ付きの **X25519 + SHA-256 + AES-256-CCM** を使います。タグは**定数時間**で比較され、復号に失敗すると平文バッファが消去されるので、認証されていないデータが使われることはありません。
- 弱い X25519 の相手の鍵（無効な共有秘密になるもの）は拒否されます。
- **秘密情報は使用後に `secureZero()` で消去されます**: 共有鍵、X25519 の生の出力、鍵スケジュール、CTR のカウンタブロック、NVS から読み込んだ鍵のレコード。
- 秘密鍵が**表示、出力、ログ記録されることはありません**。UI に表示されるのは公開鍵の先頭 4 バイトだけです。
- **鍵の生成にはハードウェアエントロピーを使います。** Wi-Fi と Bluetooth がオフなので、鍵の生成中は ESP32-S3 の RF ノイズのエントロピー源を有効にします（`bootloader_random_enable`）。パケット ID の生成器も起動のたびにハードウェアエントロピーでシードされるので、CTR のカウンタブロックと CCM のノンスが再起動をまたいで繰り返されることはなく、すべての DM は新しい乱数の `extraNonce` を持ちます。
- 保存された鍵ペアは読み込み時にチェックされます（`pub == X25519(priv)`）。壊れたレコードが中途半端に使われることはありません。

### 無線の動作と濫用対策

- **Wi-Fi と Bluetooth はオフです。** リモートからのインターフェースは LoRa だけです。
- **リージョンが選ばれるまで何も送信しません。** 初回起動時（有効なリージョンが保存されていない場合）、ユーザーがリージョンを確定するまで無線は受信のみを行います。リージョンの変更が保留中の間、あるいは Cap や無線が動作していない間は、フレームはキューに留まります。
- **デバイスは他のノードのトラフィックを中継しません**（`CLIENT_MUTE`）。
- **自動応答にはノードごとと全体のレート制限があり**、偽装した `from` 番号でデバイスに送信を続けさせることはできません:
  - NodeInfo の応答: 1 ノードにつき 12 時間に 1 回、全体で 30 秒に 1 回。
  - 復号できない PKI DM に対する NAK + NodeInfo: 1 ノードにつき 10 分に 1 回、全体で 30 秒に 1 回。
  - 鍵のないノードに DM を送ったときの NodeInfo 要求: 1 ノードにつき 60 秒に 1 回。
  - 自分の NodeInfo ブロードキャスト: 最大 30 秒に 1 回、加えて 3 時間ごとに 1 回。
  - すでに ACK した DM の再送に対する ACK: DM ごとに最大 2 回。
- **送信のペース配分**: 一度に 1 フレーム、最低 1.5 秒の間隔、6 フレームのキュー、そしてリージョンのデューティサイクルによる送信時間の予算。
- **自動あいさつ**は起動時にオフで、各ノードに最大 1 回だけ（永続化）、最大 30 秒に 1 件、キューは 10 件です。
- 直近 64 個の `(from, id)` の組による**重複の抑制**。
- **ストレージに上限があります**: 固定サイズの NVS blob、保存される相手は最大 50（枠を再利用）、あいさつ済み ID は最大 500。偽のノードを大量に送られても、ストレージが増えることはありません。

### 識別情報と鍵

- **最初の鍵が優先**: あるノード番号について最初に受信した公開鍵が保持され、異なる（または欠けた）鍵を持つ後続の NodeInfo は無視されます。DM の相手の鍵は（最大 50 まで）永続化されるので、これは再起動後も維持されます。永続化された鍵は RAM 上の別の表にも保持されるので、偽のノードを大量に送られて保存済みの相手が 100 ノードの一覧から押し出されても、その鍵を置き換えることはできません。保存された鍵は引き続き DM に使われ、そのノード番号のすべての NodeInfo との照合にも使われます。一覧がいっぱいのときは、保存済みの相手ではない鍵なしのノードから先に削除されます。
- **旧形式の DM は拒否されます**: 公開チャンネルの鍵だけで暗号化されたテキストの DM は破棄されるので、会話に表示される DM は、常に送信者の保存された鍵で PKI 認証されています。

### サプライチェーン

- ライブラリとプラットフォームは `platformio.ini` で**正確なバージョンに固定**されています。暗号ライブラリは同梱されています（`lib/crypto/`、MIT）。
- GitHub Actions は**完全なコミット SHA で固定**され、ワークフローは `contents: read` で動作し、checkout は認証情報を保持せず、Dependabot がアクションの更新を提案します。
- リリースイメージには **`bin/SHA256SUMS`** が付属します。CI は実行のたびにそれを再検証します。

## 保護されないもの

- **物理的にアクセスできれば秘密鍵を読み出せます。** ファームウェアは M5Launcher でインストールされ、M5Launcher はフラッシュ暗号化とセキュアブートを使えないため、これらはオフです。フラッシュをダンプできる人なら誰でも NVS（キー `idkey`）から鍵ペアを読み出し、DM でそのノードになりすますことができます。保存された相手、あいさつ済みの一覧、設定も読み出せます。デバイスを紛失した場合は、その識別情報が漏洩したものとみなしてください。
- **公開チャンネルは誰でも読めます。** 設計上、Meshtastic のよく知られたデフォルト鍵を使っているので、Canal 画面で送るすべてのメッセージと、すべての NodeInfo（名前、公開鍵、ハードウェアモデル）は公開されています。
- **v1 にはパケット署名（XEdDSA）がありません。** チャンネルのテキストや NodeInfo を含むブロードキャストフレームは認証されません。誰でも任意のノード番号を名乗ってチャンネルメッセージや NodeInfo を送れます。Meshtastic のデフォルトポリシーも署名なしのパケットを受け付けます。
- **鍵が分かる前のなりすまし。** ノード番号は鍵と結び付けられていません。あるノードの本物の鍵を保存する前であれば、攻撃者はそのノード番号と自分の鍵で NodeInfo を送ることができ、「最初の鍵が優先」によって攻撃者の鍵が保持されてしまいます。そのノード「宛て」の DM は攻撃者に届き、本物のノードからの DM は拒否されます。これは上流プロトコルの性質です。
- **保存済みの相手の鍵は置き換えられません。** 「最初の鍵が優先」の裏返しです。相手が工場出荷時の状態にリセットしたり NVS を消去したりして新しい鍵を得た場合、このデバイスはそれを拒否し続け、その相手との DM が使えなくなります。v1 には保存済みの鍵を 1 つだけ忘れる操作はありません（[ロードマップ](roadmap.md)を参照）。
- **メタデータは見えます。** ノード番号、名前、ハードウェアモデル、パケットのタイミング、サイズ、誰が誰に送っているか（ヘッダーの `to`/`from` は暗号化されません）は、どの受信者からも見えます。ノード ID はデバイスの MAC アドレスから導かれます。
- **DM の内容はエンドツーエンドで暗号化されますが、配信は保証されません。** 再送はなく、攻撃者は周波数を妨害したり ACK を落としたりできます。
- **物理層でのサービス妨害**（ジャミング）は対象外です。
- **チャット履歴**は RAM にしかなく、電源を切ると消えます。ロック解除されたデバイスを手にしている人からは保護されません。

## リリースの検証

リリースイメージとそのチェックサムは [`bin/`](../../bin/) にあります。

```sh
cd bin
sha256sum -c SHA256SUMS
```

両方の行が `OK` になる必要があります。`sha256sum` のない Windows では:

```bat
certutil -hashfile M5-Mesh-Hello.bin SHA256
```

結果を `SHA256SUMS` のそのファイルの行と比較してください。

チェックサムは、ファイルがリポジトリにコミットされたものと一致することを証明します。バイナリがソースと一致することを確かめるには、固定されたツールチェーンで再ビルド（`python -m platformio run -e cardputer`）して比較してください。CI もすべての push でソースからファームウェアをビルドし、CI でビルドした `firmware.bin` を独自のチェックサムとともにワークフローのアーティファクトとして公開しています。ビルドが異なるマシン間でビット単位まで再現できることは保証されていません。

## 脆弱性の報告

[SECURITY.md](../../SECURITY.md)（英語）に記載されているとおり、GitHub のプライベート脆弱性報告を使ってください。可能であれば、バージョン、リージョン、再現用のフレーム（16 進ダンプ）を含めてください。
