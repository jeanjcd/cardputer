# Архитектура

Как устроена прошивка, как через неё проходит кадр, что она хранит и сколько памяти использует. Описание относится к v0.1.0. Схемы ниже — блоки кода и, как и исходный код, оставлены на английском.

## Карта модулей

```
src/
  main.cpp        setup(): M5Cardputer.begin → App::begin → Ui::begin
                  loop():  keyboard update → Ui::handleKeys → App::tick → Ui::render
  mesh/           portable protocol core: no Arduino/ESP-IDF headers, built and tested natively
  hw/             hardware: SX1262 radio, NVS storage, persistent identity
  app/            application logic (App) and user interface (Ui)
lib/crypto/       vendored rweather/Crypto subset (AES, CTR, SHA-256, Curve25519), MIT
test/             native Unity test suites
tools/            gen_vectors.py (reference vectors), sanitize_link.py (sanitizer link flags)
```

Кратко: `src/mesh/` — переносимое ядро протокола (без заголовков Arduino/ESP-IDF, собирается и тестируется нативно); `src/hw/` — работа с оборудованием (радио SX1262, хранилище NVS, постоянная идентичность); `src/app/` — логика приложения (`App`) и интерфейс (`Ui`); `lib/crypto/` — встроенное подмножество библиотеки rweather/Crypto (MIT); `test/` — нативные наборы тестов Unity; `tools/` — вспомогательные скрипты.

### `src/mesh/` (переносимое ядро)

| [`packet`](../../src/mesh/packet.h) | Сборка исходящих кадров (текст, DM, NodeInfo, ACK/NAK), разбор и расшифровка входящих (`parseFrame`), ID пакетов, `DedupCache` |
| [`region`](../../src/mesh/region.h) | Таблица регионов, формула частоты, ограничение мощности, хеш канала, время LoRa в эфире, `AirtimeBudget` |

| [`kv`](../../src/mesh/kv.h) | Абстрактное хранилище blob «ключ/значение» (NVS на устройстве, map в тестах) |

| Модуль | Назначение |
|---|---|

### `src/app/` (приложение)

| Модуль | Назначение |
|---|---|
| [`app`](../../src/app/app.h) | Владеет всем состоянием. Обработка приёма, планирование, очередь передачи, бюджет рабочего цикла, действия с настройками, уведомления. |
| [`ui`](../../src/app/ui.h) | Четыре вкладки на дисплее 240 × 135, обработка клавиатуры, внеэкранный буфер (canvas) |

Интерфейс читает состояние только через const-методы доступа `App` и действует через его методы действий (`sendText`, `cycleRegion`, `toggleAutoGreet`, ...). `App` увеличивает счётчик версии при каждом видимом изменении. Интерфейс перерисовывается, когда счётчик меняется (не чаще раза в 50 мс), и не реже раза в секунду — для давности и уведомлений.

## Поток данных

```
                 SX1262 (DIO1 IRQ)
                        |
                 Radio::poll  ----------------------------- rx count, last RSSI
                        |
                 headerParse  -- drop: from == us / from == broadcast
                        |
                 DedupCache.contains(from, id)?  -- yes: re-ACK if it is a DM we ACKed; drop
                        |
                 parseFrame (decrypt: PKI if channel 0x00 and to == us, CTR if channel 0x08)
                        |
        +---------------+------------------+---------------------+
   undecodable     decoded, other port   NodeInfo / Text / Ack
   (PKI w/o key:        |                       |
    NAK 35 +       dedup.record           dedup.record, NodeDb.touch
    NodeInfo)      NodeDb.touch                 |
                                 +--------------+--------------+
                             NodeInfo         Text             Ack/NAK
                          NodeDb.applyUser  ChatStore.add     ChatStore: v / x
                          (first key wins)  ACK if want_ack
                          Greeter.onNodeWithKey
                          Outbox.onKeyArrived
                          NodeInfo reply (rate-limited)

   UI actions / timers
        |
   App::schedule (only when the TX queue is empty), in priority order:
        1. pending NodeInfo broadcast (boot, 3 h, rename, manual; 30 s spacing)
        2. Outbox.next  -> buildDirectText (PKI)
        3. Greeter.due  -> greeting DM
   ACKs and NAKs are inserted at the front of the queue (urgent); NodeInfo replies,
   NodeInfo requests and public texts are appended directly when they arise.
        |
   TX queue (6 frames)
        |
   App::transmitOne: >= 1.5 s since the last TX end, AirtimeBudget.allows(...)
        |
   Radio::send (blocking) -> back to RX; AirtimeBudget.record; message state ~ -> . or x
```

Словами: принятый кадр проходит через `Radio::poll` (обновляет `rx` и RSSI), разбор заголовка (отбрасываются кадры от нас самих и с широковещательного адреса), кэш дубликатов и `parseFrame`, который расшифровывает PKI или CTR. На нерасшифрованный кадр PKI без ключа отправляются NAK 35 и NodeInfo. NodeInfo обновляет NodeDb (побеждает первый ключ), передаётся в Greeter и Outbox и может вызвать ответ с ограничением частоты; тексты попадают в ChatStore (с ACK, если он запрошен); ACK/NAK меняют состояние сообщения на `v` или `x`. На выходе `App::schedule` пополняет очередь передачи только когда она пуста, по приоритету: отложенная рассылка NodeInfo, затем личные сообщения из Outbox, затем приветствия. ACK и NAK вставляются в начало очереди; ответы и запросы NodeInfo, а также публичные тексты добавляются в конец сразу при появлении.

Ключевые моменты:

- **Никакой кучи в пути приёма.** Декодированная структура `Inbound` — статический буфер, все буферы фиксированного размера с явными границами.
- **Дедупликация после разбора.** Пара записывается только после обработки кадра, поэтому личное сообщение PKI, пришедшее раньше ключа отправителя, всё ещё можно прочитать при повторной передаче.
- **Одна передача за раз.** `schedule()` пополняет очередь, только когда она пуста. `transmitOne()` отправляет не более одного кадра за проход цикла, не раньше чем через **1.5 с** после окончания предыдущего, и только если позволяет бюджет рабочего цикла региона. Иначе первый кадр (и всё за ним) ждёт, а строка состояния показывает `duty limit`.
- **Блокирующая передача.** `Radio::send` блокируется до конца передачи (до 2.2 с для 255 байт), поэтому в это время клавиши не обрабатываются.

## Хранение (NVS)

Всё хранится в разделе NVS ESP32 в пространстве имён **`meshhello`** в виде blob фиксированного размера. Чтение успешно, только если сохранённый blob имеет ровно ожидаемую длину. Байты версии и проверка полей отвергают всё остальное, и тогда используются соответствующие значения по умолчанию.

| Ключ | Размер | Структура | Когда записывается |
|---|---|---|---|
| `idkey` | 65 B | `[ver=1][priv 32][pub 32]` | Один раз, при первом запуске (или если запись отсутствует/повреждена). Проверяется при загрузке: `pub` должен быть равен X25519(`priv`, 9). |
| `settings` | 235 B | `[ver=1][region id u8][txPower i8][flags u8: bit0 custom greeting][greeting 201][longName 25][shortName 5]`; строки UTF-8, дополненные NUL | Смена мощности, имени или приветствия; смена региона (с задержкой 2 с или при выходе из Config) |
| `greeted` | 2003 B | `[ver=1][count u16 LE][500 × node number u32 LE]` | Каждый раз, когда узел поприветствован (автоматически или вручную) |
| `peer0` … `peer49` | по 89 B | `[ver=1][node number u32 LE][seq u32 LE][longName 40][shortName 8][public key 32]` | Когда мы обмениваемся личным сообщением с узлом, чей ключ известен (раз на контакт за запуск); когда заняты все 50, переиспользуется слот, записанный давнее всех |
| `region` | 1 B | ID региона | **Только чтение**, как запасной вариант от ранней диагностической сборки, если `settings` отсутствует |

ID регионов (сохраняемые): `0` ANZ, `1` BR_902, `2` US, `3` EU_868, `4` RU, `5` KR, `6` UA_868, `7` MY_919, `8` SG_923, `9` PH_868, `10` PH_915, `11` IN, `12` NZ_865, `13` NP_865, `14` KZ_863, `15` JP, `16` TW, `17` TH.

История чатов, список узлов (кроме сохранённых контактов), счётчики непрочитанного, состояние автоприветствия и бюджет эфирного времени хранятся **только в RAM**.

## Бюджет RAM

Приблизительные статические размеры на ESP32-S3 (32 бита):

| Структура | Размер | Примечания |
|---|---|---|
| `ChatStore` | ~21 KB | 96 слотов × 224 B (текст 200 байт + состояние + контакт + порядковый номер) |
| `NodeDb` | ~15 KB | 100 записей × 128 B + 50 записей о сохранённых слотах (сохранённые ключи также закреплены в RAM: 50 × 32 B) |
| Буфер строк UI | ~9 KB | 210 перенесённых строк × 44 B для отрисовки истории |
| `Outbox` | ~2.2 KB | 10 × 216 B |
| `Greeter` | ~2 KB | 500 ID поприветствованных + 10 в очереди |
| Очередь передачи | ~1.6 KB | 6 × 264 B |
| `DedupCache` | 0.5 KB | 64 × (from, id) |
| Ограничители частоты | ~0.9 KB | 3 × 32 слота |
| Буфер дисплея (canvas) | ~63 KB (куча) | 240 × 135 × 16 бит, выделяется один раз при старте; если выделить не удалось, UI рисует прямо на дисплее |

Blob `greeted` (2 KB) собирается на стеке во время загрузки или сохранения.
