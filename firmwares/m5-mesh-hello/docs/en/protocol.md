# Protocol reference

This page describes exactly what M5-Mesh-Hello v0.1.0 puts on the air and what it accepts. It is a reference for implementers. Everything here is derived from the code in [`src/mesh/`](../../src/mesh/) and checked against reference vectors generated by [`tools/gen_vectors.py`](../../tools/gen_vectors.py) (Python `cryptography`).

The firmware implements a small, interoperable subset of the [Meshtastic](https://meshtastic.org) protocol. Upstream sources it mirrors:

- Radio, regions and frequency: [`src/mesh/RadioInterface.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/RadioInterface.cpp), [`RadioInterface.h`](https://github.com/meshtastic/firmware/blob/master/src/mesh/RadioInterface.h)
- Encryption: [`src/mesh/CryptoEngine.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/CryptoEngine.cpp), [`src/mesh/aes-ccm.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/aes-ccm.cpp)
- Routing, ACKs and PKI decisions: [`src/mesh/Router.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/Router.cpp), [`src/mesh/ReliableRouter.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/ReliableRouter.cpp)
- Channels and channel hash: [`src/mesh/Channels.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/Channels.cpp)
- Node database and key handling: [`src/mesh/NodeDB.cpp`](https://github.com/meshtastic/firmware/blob/master/src/mesh/NodeDB.cpp)
- Protobufs: [`meshtastic/mesh.proto`](https://github.com/meshtastic/protobufs/blob/master/meshtastic/mesh.proto), [`meshtastic/portnums.proto`](https://github.com/meshtastic/protobufs/blob/master/meshtastic/portnums.proto)

## Physical layer

LoRa, Meshtastic **LongFast**: BW 250 kHz, SF 11, CR 4/5, sync word `0x2B`, 16-symbol preamble, explicit header, payload CRC on. The centre frequency is computed from the region. See [frequencies.md](frequencies.md#how-the-frequency-is-computed). One LoRa frame is at most 255 bytes: a 16-byte header plus up to 239 bytes of encrypted payload.

## On-air header (16 bytes, little-endian)

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 4 | `to` | Destination node number; `0xFFFFFFFF` = broadcast |
| 4 | 4 | `from` | Sender node number |
| 8 | 4 | `id` | Packet ID |
| 12 | 1 | `flags` | See below |
| 13 | 1 | `channel` | Channel hash (`0x08` for the default channel), or `0x00` for PKI |
| 14 | 1 | `next_hop` | We send 0 |
| 15 | 1 | `relay_node` | We send the low byte of our node number |

`flags`:

| Bits | Mask | Field | We send |
|---|---|---|---|
| 0–2 | `0x07` | `hop_limit` | 3 |
| 3 | `0x08` | `want_ack` | 1 for PKI direct texts, 0 otherwise |
| 4 | `0x10` | `via_mqtt` | 0 |
| 5–7 | `0xE0` (`>> 5`) | `hop_start` | 3 |

Code: [`header.cpp`](../../src/mesh/header.cpp), [`packet.cpp`](../../src/mesh/packet.cpp) `fillHeader`.

## Channel encryption (AES-128-CTR)

All frames except PKI direct messages are encrypted with the default channel key:

- **Key** (AES-128; this is what the PSK shorthand `AQ==`, index 1, expands to):
  `d4 f1 bb 3a 20 29 07 59 f0 bc ff ab cf 4e 69 01`
- **Channel name**: `LongFast`.
- **Channel hash** (header byte 13): XOR of all name bytes, XORed with all key bytes = **`0x08`**.
- **Counter block** (16 bytes):

  | Bytes | Content |
  |---|---|
  | 0–7 | packet `id` as u64 little-endian (bytes 4–7 are zero) |
  | 8–11 | `from` as u32 little-endian |
  | 12–15 | block counter, 32-bit **big-endian**, starting at 0 |

- The plaintext is an encoded `Data` protobuf. Encryption and decryption are the same XOR operation.

Code: [`crypto.cpp`](../../src/mesh/crypto.cpp) `ctrCrypt`, [`region.cpp`](../../src/mesh/region.cpp) `kDefaultKey` / `channelHash`.

## PKI direct messages (X25519 + SHA-256 + AES-256-CCM)

Current Meshtastic firmware sends text DMs only with public-key encryption (PKI). M5-Mesh-Hello does the same.

1. **Key pair**: X25519. The private key is 32 random bytes from the hardware RNG, clamped per RFC 7748 (`k[0] &= 248; k[31] &= 127; k[31] |= 64`). Public key = X25519(priv, 9). It is generated once and stored in NVS.
2. **Shared key**: `key = SHA-256(X25519(our_priv, peer_pub))`, 32 bytes. Peer keys that produce an all-zero or otherwise invalid shared secret (weak points) are rejected.
3. **Cipher**: AES-256-CCM (RFC 3610), **tag length M = 8**, length field L = 2, **13-byte nonce**, no associated data.
4. **Nonce** (13 bytes):

   | Bytes | Content |
   |---|---|
   | 0–3 | packet `id`, u32 little-endian |
   | 4–7 | `extraNonce`, u32 little-endian |
   | 8–11 | `from`, u32 little-endian |
   | 12 | `0x00` |

   This layout looks odd, but it is what upstream does. Meshtastic builds a 16-byte buffer as `id (u64 LE) | from (u32 LE) | 0`, then copies `extraNonce` over bytes 4–7, which are the high half of the u64 id and are always zero. CCM uses the first 13 bytes. An implementation must mirror this exactly.
5. **Wire format** of the payload after the 16-byte header: `ciphertext | tag (8 bytes) | extraNonce (4 bytes, LE)`. The overhead is 12 bytes, so the largest plaintext `Data` is 239 − 12 = 227 bytes.
6. **Header**: `channel = 0x00`, `to` = the recipient's node number, `want_ack = 1`.
7. `extraNonce` is a fresh 32-bit random value for every message.

On receive, a frame is treated as PKI when `channel == 0x00` **and** `to` is our node number. The sender's stored public key is needed. If it is unknown, the frame cannot be decrypted (see [Unknown-key handling](#unknown-key-handling)). Tags are compared in constant time, and on failure the plaintext buffer is wiped and the frame is dropped.

Code: [`crypto.cpp`](../../src/mesh/crypto.cpp) `x25519Shared` / `pkiEncrypt` / `pkiDecrypt`, [`aes_ccm.cpp`](../../src/mesh/aes_ccm.cpp).

## Which key is used for what

| Frame | Encryption | `channel` byte |
|---|---|---|
| Text to the public channel (broadcast) | Channel key (CTR) | `0x08` |
| Text to one node (DM) | **PKI** (CCM) | `0x00` |
| NodeInfo (broadcast or directed) | Channel key | `0x08` |
| Routing ACK / NAK | Channel key | `0x08` |

On receive:

- Frames with channel hash `0x08` are decrypted with the default key. Any other channel hash except `0x00` is ignored, but it still counts in `rx`.
- **Legacy DMs are rejected**: a `TEXT_MESSAGE_APP` frame encrypted with the channel key and addressed to a single node (not broadcast) is dropped, as in the official firmware. Text DMs must be PKI.
- Frames with `from` equal to our own node number or to `0xFFFFFFFF` are ignored.

## Protobuf subset

Hand-written encoder/decoder ([`pb.cpp`](../../src/mesh/pb.cpp)); unknown fields are skipped; malformed or truncated input is rejected.

**`Data`** (the decrypted payload):

| Field | No. | Type | Use |
|---|---|---|---|
| `portnum` | 1 | varint | `1` TEXT_MESSAGE_APP, `4` NODEINFO_APP, `5` ROUTING_APP; others are recognised as activity only |
| `payload` | 2 | bytes | ≤ 233 bytes accepted |
| `want_response` | 3 | varint (bool) | Set on our boot NodeInfo and NodeInfo requests |
| `dest` | 4 | fixed32 | Decoded, not used |
| `source` | 5 | fixed32 | Decoded, not used |
| `request_id` | 6 | fixed32 | In ACK/NAK: the ID of the packet being acknowledged |
| `reply_id` | 7 | fixed32 | Decoded, not used |

**`User`** (payload of NODEINFO_APP):

| Field | No. | Type | We send |
|---|---|---|---|
| `id` | 1 | string | `!%08x` of our node number |
| `long_name` | 2 | string | Our long name, cut to 24 bytes at a UTF-8 boundary |
| `short_name` | 3 | string | Our short name (≤ 4 bytes) |
| `hw_model` | 5 | varint | `112` (M5STACK_CARDPUTER_ADV) |
| `role` | 7 | varint | `1` (CLIENT_MUTE) |
| `public_key` | 8 | bytes | Our 32-byte X25519 public key |

A received `User` whose `public_key` is present but not exactly 32 bytes is rejected as a whole. Fields 4 (`macaddr`, deprecated) and 6 (`is_licensed`) are skipped.

**`Routing`** (payload of ROUTING_APP):

| Field | No. | Type | Use |
|---|---|---|---|
| `error_reason` | 3 | varint (enum) | `0` NONE = ACK; anything else = NAK. We send `35` PKI_UNKNOWN_PUBKEY |

## ACK and NAK

- **Sending an ACK**: for every PKI DM addressed to us with `want_ack`, we send a `ROUTING_APP` frame to the sender with `request_id` = the DM's packet ID and `Routing{error_reason = NONE}` encoded explicitly as bytes `18 00`. It is channel-encrypted, hop limit 3, without `want_ack`. If the same DM arrives again (a retransmission because our ACK was lost), we ACK it again. The last 8 ACKed `(from, id)` pairs are remembered for this.
- **Receiving**: a ROUTING_APP frame addressed to us with a non-zero `request_id` is an ACK if `error_reason` is absent or 0. Proto3 omits zero values, so an empty `Routing` message also means NONE. The matching message changes from sent (`.`) to acknowledged (`v`). A non-zero `error_reason` is a NAK: the message is marked failed (`x`).
- We never retransmit a DM automatically.

## Unknown-key handling

- **Sending to a node without a key**: the DM is held (state `?`), and we send our NodeInfo **directly** to that node with `want_response = 1` (at most once per 60 s per node). When its NodeInfo with a key arrives, held DMs are released.
- **Receiving a PKI DM from a node without a key**: we send a NAK `Routing{error_reason = 35 (PKI_UNKNOWN_PUBKEY)}` with `request_id` = its packet ID, plus our NodeInfo with `want_response = 1`. Limits: once per 10 minutes per node and once per 30 s globally. Undecodable frames are **not** added to the duplicate cache, so the sender's retry can be decrypted once the key has arrived.

## NodeInfo

- We broadcast our NodeInfo at boot (with `want_response`), every 3 hours, after a name change, and on request from the Config screen. Manual and rename broadcasts are spaced at least 30 s apart.
- We answer a received NodeInfo that has `want_response` (broadcast or addressed to us) with our NodeInfo sent directly to that node, without `want_response`. Limits: once every 12 h per node and once every 30 s globally, so that spoofed senders cannot keep us on the air.

## First key wins

The first 32-byte public key received for a node number is stored and never replaced, as in Meshtastic's NodeDB. A later `User` for that node is applied only if it carries the **same** key. If the key differs or is missing, the whole update is ignored, names included. Keys of DM peers are persisted (up to 50) so that the rule survives reboots. Our own key is generated once and never changes for the same reason.

The receiver does not check a node number against its key. Before a node's key is known, anyone can send a NodeInfo claiming that node number with their own key, and that key will win. This is an upstream protocol property; see [security.md](security.md).

## Node number

Our node number is the **last 4 bytes of the factory MAC** address, big-endian (`mac[2] << 24 | mac[3] << 16 | mac[4] << 8 | mac[5]`), as the official firmware does. If the MAC cannot be read or yields a reserved value (`< 4` or `0xFFFFFFFF`), an FNV-1a hash of the public key is used instead. The node ID string is `!` followed by the number in 8 lowercase hex digits.

## Packet IDs

`id = (rnd << 10) | (counter & 0x3FF)`, never 0. `rnd` is a 32-bit value from an xorshift64* generator seeded from the hardware RNG at every boot, so IDs (and therefore CTR counter blocks and CCM nonces) do not repeat across reboots. `counter` increments on every ID. The same scheme is used upstream.

## Duplicate suppression

A ring of the last **64** `(from, id)` pairs. A frame whose pair is in the cache is ignored, except that a duplicate DM we already ACKed is ACKed again. A pair is recorded only after the frame was successfully handled. Frames that failed to decrypt or decode are not recorded.

## Hop limit and relaying

Every frame we originate has `hop_limit = hop_start = 3`, the Meshtastic default. We **never relay** frames from other nodes: our NodeInfo declares the role `CLIENT_MUTE`, and the firmware has no rebroadcast path.

## Not implemented in v1

XEdDSA packet signatures (upstream's default policy accepts unsigned packets), channels other than the default primary, custom PSKs and AES-256-CTR channels, presets other than LongFast, position, telemetry, traceroute, store-and-forward, MQTT. See [roadmap.md](roadmap.md).
